### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Пользователи могут удаленно управлять отоплением, включать/выключать отопление в своих домах
- Система поддерживает синхронное взаимодействие

**Мониторинг температуры:**

- Пользователи могут просматривать текущую температуру в своих домах через веб-интерфейс
- Система получает данные о температуре с датчиков, установленных в домах
- Каждая установка сопровождается выездом специалиста по подключению системы отопления в доме к текущей версии системы.
- Самостоятельно подключить свой датчик к системе пользователь не может

### 2. Анализ архитектуры монолитного приложения

Язык программирования: Java
База данных: PostgreSQL
Архитектура: Монолитная, все компоненты системы (обработка запросов, бизнес-логика, работа с данными) находятся в рамках одного приложения.
Взаимодействие: Синхронное, запросы обрабатываются последовательно.
Масштабируемость: Ограничена, так как монолит сложно масштабировать по частям.
Развёртывание: Требует остановки всего приложения.

### 3. Определение доменов и границы контекстов

Домены
1) Домен устройств
	Поддомен управления устройством
		Контекст получения информации с датчиков (температура, наблюдение за домом)
		Контекст управления устройствами (температурой, автоматическими воротами...)
		Контекст сценариев управления
	Поддомен регистрации, подключения и отключения устройства
		Контекст регистрации, подключения и отключения устройства
2) Домен пользователей и доступа
	Поддомен управление аккаунтами
	Поддомен безопасности и авторизации
	Общий контекст управления аккаунтами
3) Домен биллинга / подписки
	Поддомен управления тарифами и подписками
		Контекст управления тарифами и подписками
	Поддомен оплаты (+ интеграции с платежными системами)
		Контекст оплаты (+ интеграции с платежными системами) (в будущем можно интеграции вынести в отдельный контекст)

### **4. Проблемы монолитного решения**

1) Трудно масштабировать отдельные части системы. Нельзя независимо масштабировать, например, только подсистему управления устройствами
2) Текущее решение не ориентировано на геораспределенную среду (умные поселки)
3) Сложно и долго добавлять новый функционал, так как это может повлиять на весь код и требует тщательного тестирования всего функционала.
Например, добавление сценариев или поддержки новых типов устройств может затронуть весь код
4) Конфликты при командной разработке - изменения, которые вносят разработчики, могут мешать друг другу
5) Низкая надежность - любая ошибка положит сразу весь функционал
